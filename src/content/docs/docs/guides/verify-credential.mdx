PDTF credential verification has four jobs: validate the VC structure, verify the issuer's signature, confirm through OpenID Federation that the issuer is trusted for the claimed paths, and check the credential has not been revoked or suspended.

In `@pdtf/core`, the easiest way to do that is `VcValidator`. It combines DID resolution, proof verification, federation trust resolution, and Bitstring Status List checking in one pipeline.

:::note[Provisional]
The examples on this page use the Data Integrity representation (`DataIntegrityProof`, `eddsa-jcs-2022`, `credentialStatus`) that the current libraries implement. The spec's provisional securing mechanism is SD-JWT-VC with Token Status List: see [02 §2.4](/specs/02-vc-data-model/#24-securing-mechanism) and [14 §1](/specs/14-credential-revocation/#1-purpose) (consultation [Q20](/consultation/#q20-credential-format--securing-mechanism)).
:::

`DidResolver` resolves `did:key` locally and `did:web` over HTTPS. `FederationRegistryResolver` resolves the issuer's trust chain to the PDTF Trust Anchor at `https://propdata.org.uk` and caches it. `VcValidator` orchestrates the checks. There is no separate Trusted Issuer Registry: OpenID Federation replaced it ([04 §1.1](/specs/04-openid-federation/#11-why-openid-federation)). See [Verify Trust](/docs/guides/integrate-federation/) for the resolver on its own.

## 2. Supply the credential paths

Federation authorisation is path-based, not issuer-wide: the issuer's `pdtf-verified-issuer` Trust Mark lists the entity:path combinations it may assert in `delegation.authorised_paths`. That means you should tell the validator which PDTF entity paths the credential is asserting.

For an EPC credential, that might be:

## 3. Validate the credential

The result is stage-based:

- `structure`: required VC and PDTF fields
- `signature`: resolves the issuer DID, checks `verificationMethod`, confirms the key is in `assertionMethod`, then runs `verifyProof`
- `trust`: resolves the issuer's Entity Configuration, walks `authority_hints` to the Trust Anchor, verifies the Trust Mark, and checks `delegation.authorised_paths` covers the claimed paths
- `status`: fetches the signed Bitstring Status List credential, verifies it, and checks the credential's revocation (and, where present, suspension) bit

The trust result reports the issuer's level from `delegation.trust_level`: `root_issuer`, `trusted_proxy` or `account_provider`. The fourth level, `assertion`, is never returned by federation resolution. It applies to a credential whose `evidence` is a `UserAttestation` (a person's own statement), so read it from the evidence. See [04 §8](/specs/04-openid-federation/#8-trust-levels).

## 4. What the validator enforces

`VcValidator` is intentionally fail-closed in the places that matter:

- `issuer` must match the DID used in `proof.verificationMethod`
- the verification method must exist in the DID document
- the verification method must be listed in `assertionMethod`
- `credentialStatus` must be present for revocation checking
- a set revocation or suspension bit means the credential is rejected
- if federation trust resolution fails, the credential is rejected; there is no fallback trust level

That aligns with the PDTF model: a valid signature is not enough on its own. When composing transaction state, a credential that fails trust resolution is excluded and logged as unauthorised ([07 §3.3](/specs/07-state-assembly/#33-pre-assembly-filtering)).

## 5. Verify just the proof, if you need a lower-level check

If you already resolved the public key yourself, you can call `verifyProof` directly:

<Tabs syncKey="language">
  <TabItem label="TypeScript">
    ```ts
    import { DidResolver, verifyProof, type VerifiableCredential } from '@pdtf/core';
    import { base58btc } from 'multiformats/bases/base58';

    const vc: VerifiableCredential = await loadCredentialSomehow();
    const resolver = new DidResolver();

    const vm = vc.proof!.verificationMethod;
    const issuerDid = vm.split('#')[0]!;
    const didDoc = await resolver.resolve(issuerDid);
    const method = didDoc.verificationMethod!.find((m) => m.id === vm)!;

    const decoded = base58btc.decode(method.publicKeyMultibase!);
    const publicKey = decoded[0] === 0xed && decoded[1] === 0x01
      ? decoded.slice(2)
      : decoded;

    const ok = verifyProof({
      document: vc,
      publicKey,
    });

    console.log({ ok });
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust
    use pdtf_core::signer::proof::verify_proof;
    use pdtf_core::did::resolver::DidResolver;

    let resolver = DidResolver::new()?;
    let vc = load_credential_somehow().await?;

    let vm = vc.proof.as_ref().unwrap().verification_method.clone();
    let issuer_did = vm.split('#').next().unwrap();
    let did_doc = resolver.resolve(issuer_did).await?;

    let method = did_doc.verification_method.iter()
        .find(|m| m.id == vm)
        .expect("Verification method not found");

    let public_key = method.decode_public_key()?;
    let ok = verify_proof(&vc, &public_key)?;

    println!("Proof valid: {ok}");
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    from pdtf_core import verify_proof, DidResolver

    resolver = DidResolver()
    vc = load_credential_somehow()

    vm = vc["proof"]["verificationMethod"]
    issuer_did = vm.split("#")[0]
    did_doc = resolver.resolve(issuer_did)

    method = next(m for m in did_doc["verificationMethod"] if m["id"] == vm)
    ok = verify_proof(vc_json=json.dumps(vc), public_key_hex=method["publicKeyHex"])

    print(f"Proof valid: {ok}")
    ```
  </TabItem>
  <TabItem label=".NET">
    ```csharp

    var vc = LoadCredentialSomehow();

    var vm = vc.Proof.VerificationMethod;
    var issuerDid = vm.Split('#')[0];
    var didDoc = await resolver.Resolve(issuerDid);

    var method = didDoc.VerificationMethod.First(m => m.Id == vm);
    var publicKey = method.DecodePublicKey();

    var ok = PdtfCore.VerifyProof(vc, publicKey);
    Console.WriteLine($"Proof valid: {ok}");
    ```

Use this lower-level path when you are embedding verification into a custom flow, but prefer `VcValidator` for production verification because it also checks federation authorisation and revocation.

## 6. Recommended production pattern

For most PDTF consumers, the right flow is:

1. Parse the VC JSON.
2. Call `validator.validate(...)` with `credentialPaths`.
3. Reject if any stage fails.
4. Log `warnings` and the trust result (trust chain, Trust Mark, trust level) for audit.
5. Cache DID documents, trust chains, and status lists for short periods only. Trust Marks are short-lived (days), so do not cache them beyond their `exp`.

If the credential is about access or authority, such as SellerCapacity, Offer, Gift, Representation, or TransactionRole, do not skip the status check. Revocation is what turns an old mandate into an invalid one, and suspension holds a disputed one ([14 §8](/specs/14-credential-revocation/#8-suspension-vs-revocation)).
